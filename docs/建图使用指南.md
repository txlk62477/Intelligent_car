# 小车 Cartographer 建图使用指南

本文用于当前实车的纯建图测试。底盘 `leap_low_driver` 已通过 micro-ROS 发布
`/scan`、`/odom` 和 `/imu`，因此建图时不需要连接本机 `/dev/lidar`，也不要再启动
第二个雷达驱动。

## 1. 数据链路与 TF 归属

```text
/odom（MCU 原始里程计） ─┐
                         ├─> Sensor Fusion EKF ─> /odometry/filtered
/imu（MCU 原始 IMU） ────┘                           │
                                                    └─> odom -> base_link

/scan（frame_id=laser_frame） ─> Cartographer ─> map -> odom、/map
```

- `/odom` 是原始输入，保留该话题是正常的；它不再直接发布 TF。
- `/odometry/filtered` 是新的融合里程计，Cartographer 只订阅该话题。
- EKF 是 `odom -> base_link` 的唯一发布者。
- Cartographer 只发布 `map -> odom`。
- 建图启动文件发布固定的 `base_link -> laser_frame`；融合启动文件发布固定的
  `base_link -> imu_link`。
- 旧的 raw-odom TF 广播器已删除，避免与 EKF 重复发布 `odom -> base_link`。

## 2. 首次安装与构建

Cartographer 依赖只需安装一次：

```bash
sudo apt-get update
sudo apt-get install -y ros-jazzy-cartographer ros-jazzy-cartographer-ros
```

代码更新后构建：

```bash
cd /home/lk/car/software/leap_ros_ws
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-up-to xuegecar_cartographer
source install/setup.bash
```

## 3. 启动前检查

先确认 micro-ROS 已连接，并且只有一个底盘发布者：

```bash
ros2 topic list
ros2 topic info /scan -v
ros2 topic info /odom -v
ros2 topic info /imu -v
ros2 topic echo /scan --once --field header --qos-profile best_available
```

必须能看到：

- `/scan` 类型为 `sensor_msgs/msg/LaserScan`，`frame_id` 为 `laser_frame`。
- `/odom` 类型为 `nav_msgs/msg/Odometry`，父坐标系为 `odom`，子坐标系为
  `base_link`。
- `/imu` 类型为 `sensor_msgs/msg/Imu`，`frame_id` 为 `imu_link`。
- 三者持续收到新数据，而不是只有话题名称。

### micro-ROS Agent 的 Docker 启动参数

这是 UDP 网络通信，不需要挂载 `/dev` 或使用 `--privileged`。启动容器：

```bash
sudo docker run --rm -it \
  --name micro-ros-agent \
  --user "$(id -u):$(id -g)" \
  --network host \
  --ipc host \
  -e MICROROS_DISABLE_SHM=0 \
  -e ROS_LOG_DIR=/tmp/ros-log \
  microros/micro-ros-agent:${ROS_DISTRO:-jazzy} \
  udp4 --port 8888 -v6
```

`--ipc host` 让容器与宿主机共享 IPC。小车的 `/scan` 是包含 360 个距离点的
`LaserScan` 大消息；保留该参数可让 Fast DDS 在条件允许时使用共享内存，避免
容器到宿主机的数据再次经过受 MTU 限制的网络传输。

镜像默认设置 `MICROROS_DISABLE_SHM=1`，因此必须显式覆盖为 `0`。同时通过
`--user "$(id -u):$(id -g)"` 让 Agent 与当前宿主用户使用相同的 UID/GID，避免
Fast DDS 共享内存文件由容器内 `root` 创建后，宿主 ROS 2 节点因权限不同而无法
接收消息。不要写成 `--user lk`：用户名由容器内的 `/etc/passwd` 解析，而镜像中
不一定存在 `lk`；动态读取宿主用户的数字 UID/GID 更可靠。`ROS_LOG_DIR` 指向容器
普通用户可写的 `/tmp/ros-log`。

如果提示容器名 `micro-ros-agent` 已被占用，先确认旧实例：

```bash
sudo docker ps -a --filter name=micro-ros-agent
```

需要重启时执行：

```bash
sudo docker stop micro-ros-agent

sudo docker run --rm -it \
  --name micro-ros-agent \
  --user "$(id -u):$(id -g)" \
  --network host \
  --ipc host \
  -e MICROROS_DISABLE_SHM=0 \
  -e ROS_LOG_DIR=/tmp/ros-log \
  microros/micro-ros-agent:${ROS_DISTRO:-jazzy} \
  udp4 --port 8888 -v6
```

检查启动时间和 IPC 参数是否真正生效：

```bash
sudo docker inspect \
  --format 'User={{.Config.User}} IPC={{.HostConfig.IpcMode}} Started={{.State.StartedAt}}' \
  micro-ros-agent
```

正常应包含当前用户的数字 UID/GID（例如 `User=1000:1000`）和 `IPC=host`。不要
并行启动两个 micro-ROS Agent；两个进程争用 UDP `8888` 会造成底盘会话反复断开。

另开终端检查底盘话题：

```bash
ros2 topic list
ros2 topic hz /odom
ros2 topic hz /imu
```

如果看不到话题，检查主机、容器和底盘 MCU 使用的 `ROS_DOMAIN_ID` 是否一致：

```bash
echo "$ROS_DOMAIN_ID"
docker inspect micro-ros-agent --format '{{range .Config.Env}}{{println .}}{{end}}' | grep ROS_DOMAIN_ID
```

未显式设置 `ROS_DOMAIN_ID` 时默认为 `0`。使用其他 Domain 时，在
`docker run` 中增加 `-e ROS_DOMAIN_ID=<编号>`，宿主机终端也要导出同一个值。

## 4. 推荐启动方式：融合与建图分开运行

### 终端 A：启动融合

```bash
cd /home/lk/car/software/leap_ros_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch xuegecar_sensor_fusion fusion.launch.py
```

确认新的 odom 已输出，并且 `/clock` 与 `/odometry/filtered` 各只有一个发布者：

```bash
ros2 topic hz /odometry/filtered
ros2 topic info /clock -v
ros2 topic info /odometry/filtered -v
```

### 终端 B：启动纯建图

```bash
cd /home/lk/car/software/leap_ros_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch xuegecar_cartographer cartographer.launch.py
```

该命令默认：

- `start_fusion:=false`：使用终端 A 已运行的融合节点。
- `start_lidar:=false`：使用 MCU 已发布的 `/scan`。
- `start_rviz:=true`：打开建图界面。

无图形界面时使用：

```bash
ros2 launch xuegecar_cartographer cartographer.launch.py start_rviz:=false
```

如果此前没有单独启动融合，也可以一条命令启动融合和建图：

```bash
ros2 launch xuegecar_cartographer cartographer.launch.py start_fusion:=true
```

不要在融合已经运行时再使用 `start_fusion:=true`。两套 `/clock` 和两套 EKF
会导致时间回退、TF 缓存反复清空，并可能让 Cartographer 因 odom 时间乱序退出。

## 5. 检查建图是否正常

另开终端并加载工作区：

```bash
cd /home/lk/car/software/leap_ros_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
```

检查数据与地图：

```bash
ros2 topic hz /scan
ros2 topic hz /odometry/filtered
ros2 topic hz /map
ros2 topic info /odometry/filtered -v
ros2 run tf2_ros tf2_echo map laser_frame
```

正常结果应满足：

- `/odometry/filtered` 只有一个 EKF 发布者。
- `/odometry/filtered` 的订阅者包含 `cartographer_node`。
- TF 链完整：`map -> odom -> base_link -> laser_frame`。
- 小车移动并收到雷达帧后，RViz 中地图持续扩展。

如果 `/scan` 出现在 `ros2 topic list` 中，但 `ros2 topic hz /scan` 长时间没有统计，
说明只有发布端实体、没有实际雷达帧；此时应检查雷达供电和 MCU 到主机的网络链路。

## 6. 键盘控制建图

另开终端：

```bash
cd /home/lk/car/software/leap_ros_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

建图时低速、平稳移动，转弯不要过快，并尽量回到走过的区域形成回环。键盘控制和
Agent Gateway 都会发布 `/cmd_vel`，二者不能同时运行。测试区域应清空障碍并有人看护。

## 7. 保存地图

建图结束后先让小车停稳，等待几秒让最后一轮地图更新完成，并保持 Cartographer
继续运行。然后创建地图目录：

```bash
mkdir -p /home/lk/car/data/maps
```

直接把当前 `/map` 保存为供 Nav2 使用的栅格地图：

```bash
ros2 run nav2_map_server map_saver_cli \
  -f /home/lk/car/data/maps/car_map
```

`-f` 后面的值同时指定保存目录和地图名称，不要添加扩展名。上面的命令会生成：

```text
/home/lk/car/data/maps/car_map.pgm
/home/lk/car/data/maps/car_map.yaml
  
确认文件生成后，再在建图终端按 `Ctrl+C` 停止节点：

```bash
ls -lh \
  /home/lk/car/data/maps/car_map.pgm \
  /home/lk/car/data/maps/car_map.yaml
```

## 8. 录制排查数据

需要复现建图问题时，在建图开始前运行：

```bash
ros2 bag record \
  -o /home/lk/car/data/mapping_test_$(date +%Y%m%d_%H%M%S) \
  /scan /odom /imu \
  /fusion/odom_valid /fusion/imu_valid /odometry/filtered \
  /clock /tf /tf_static /map /submap_list
```

录制完成按 `Ctrl+C`。排查时重点检查原始 `/odom`、融合后的
`/odometry/filtered`、雷达 `/scan` 以及完整 TF 链。

## 9. 常见问题

### 持续出现 `Detected jump back in time`

先检查发布者数量：

```bash
ros2 topic info /clock -v
ros2 topic info /odometry/filtered -v
```

如果各有两个同名发布者，说明融合启动了两次。分别在对应终端按 `Ctrl+C`，只保留
一套 `fusion.launch.py`。

### Cartographer 提示 `Queue waiting for data: (0, scan)`

`/scan` 没有实际数据或频率不稳定。检查：

```bash
ros2 topic hz /scan
ros2 topic echo /scan --once --field header --qos-profile best_available
```

当前 MCU 已直接发布 `/scan`，不要为此启动 `camsense_lidar_node`。

如果命令只反复显示下面内容，而没有打印 `LaserScan` 的 header 和角度字段：

```text
A message was lost!!!
```

说明 `/scan` 只有 DDS 发布者实体，但完整雷达帧没有到达宿主机订阅者。可以保存
Agent 调试日志：

```bash
sudo docker logs --tail 200 micro-ros-agent > /home/lk/car/test.txt 2>&1
```

当前实测的雷达数据路径有以下特征：

- MCU 发出的 XRCE-DDS UDP 包约 `1512` 字节。
- Agent 成功收到包，并尝试向 DDS 写出约 `1500` 字节的 `LaserScan`。
- 主机活动接口 MTU 实测为 `1360` 或 `1410` 字节。
- 即使容器显示 `IPC=host`，本机仍可能没有采用可用的跨容器共享内存路径，
  主机订阅者仍会报告 `message lost`。

因此 `IPC=host` 是正确的 Docker 启动参数，但不能单独证明雷达大消息已经恢复。
必须以 `ros2 topic echo /scan --once --no-arr --qos-profile best_available` 能输出
完整消息头为准。在该检查通过前不要启动 Cartographer；否则只会持续等待
`scan`，无法生成地图。后续如仍丢包，需要为 Fast DDS 配置小于接口 MTU 的分片
尺寸，或调整 MCU 的雷达消息大小。

### 没有 `/map`

依次确认 `/scan`、`/odometry/filtered` 和 TF：

```bash
ros2 topic hz /scan
ros2 topic hz /odometry/filtered
ros2 run tf2_ros tf2_echo odom laser_frame
```

任一环节没有持续数据，Cartographer 都无法生成有效地图。
